# Security Review: Account Linking Logic

This document outlines the security review findings for the new account linking and merging functionality, spanning `api/src/routes/auth.ts`, `api/src/routes/admin.ts`, and `api/src/lib/merge.ts`.

## 1. Social Engineering / Privilege Escalation (Critical)

> [!CAUTION]
> A critical vulnerability exists in the directional flow of the account merge process that allows for **Privilege Escalation** and **Account Takeover** via Social Engineering.

**The Flaw:**
In `/me/link`, the logged-in user (Account B) submits a link token generated by Account A. Account B is then merged *into* Account A, and `mergeAccounts` explicitly promotes Account A's global role and trip roles to the highest available rank between the two accounts.

**Attack Vector:**
1. An attacker with a `viewer` account (Account A) triggers `/me/link-token` and receives a token.
2. The attacker socially engineers an `admin` (Account B) into entering this token into the "Link Accounts" UI.
3. The Admin's session calls `/me/link` with the attacker's token.
4. The backend merges the Admin *into* the Attacker's account.
5. The Attacker's account (Account A) is promoted to `admin`. The Attacker retains their original email on the account, granting them full, persistent `admin` access, while stealing all the original Admin's data.

**Recommendation:**
- **UI Confirmation:** The `/me/link` flow should require a 2-step process. Submitting the token should first return the details of the destination account (e.g., "You are about to merge your account into `attacker@email.com`"). The user must then explicitly confirm the merge.
- **Role Promotion Guardrails:** Re-evaluate if roles should be automatically promoted during linking, or if manual admin intervention should be required to promote the merged account.

## 2. Time-Of-Check-To-Time-Of-Use (TOCTOU) Race Condition (High)

> [!WARNING]
> The token validation and deletion in `/me/link` is not atomic, leading to potential race conditions under high concurrency.

**The Flaw:**
In `api/src/routes/auth.ts`, the code selects the token, checks its expiration, and then issues a separate `DELETE` query.
```typescript
const tokenRows = await db.select().from(accountLinkTokens).where(eq(accountLinkTokens.token, token)).limit(1);
// ... checks ...
await db.delete(accountLinkTokens).where(eq(accountLinkTokens.id, linkToken.id));
```

**Attack Vector:**
If an attacker triggers multiple rapid concurrent requests to `/me/link` with the same valid token (e.g., using different secondary accounts), all requests may complete the `SELECT` check before any reaches the `DELETE` statement. This results in `mergeAccounts` being called concurrently for multiple users into the same destination account, leading to race conditions and potential data corruption.

**Recommendation:**
Perform the deletion atomically. Drizzle allows returning the deleted rows (which D1/SQLite supports).
```typescript
const deletedToken = await db
  .delete(accountLinkTokens)
  .where(eq(accountLinkTokens.token, token))
  .returning();

if (!deletedToken.length) return c.json({ error: "Token not found or already used" }, 404);
```

## 3. Lack of Database Transactions in `mergeAccounts` (Medium)

> [!WARNING]
> The `mergeAccounts` function executes six separate database mutations sequentially without a wrapping SQL transaction.

**The Flaw:**
The comments in `api/src/lib/merge.ts` explicitly state: *"Operations are ordered so that partial failure leaves the merge user intact as a 'ghost' rather than losing data."*

While ordering mitigates total data loss, a partial failure (e.g., server crash or isolate termination during step 3) will leave the database in an inconsistent state. For example, the `userEmails` table might assign the merge user's emails to the destination account, but the `participants` mapping remains on the old user. This creates zombie records and unexpected authentication states.

**Recommendation:**
Wrap the entire `mergeAccounts` sequence in a Database Transaction (`db.transaction(async (tx) => { ... })`). This guarantees the merge happens completely atomically.

## 4. No Implicit Rate Limiting (Low)

> [!NOTE]
> Generate/Consume token endpoints do not have explicit rate limiting.

**The Flaw:**
`crypto.randomUUID()` provides sufficient entropy (122 bits) to prevent brute-forcing a token within its 15-minute lifespan. However, an attacker could rapidly spam `/me/link-token` to fill the `accountLinkTokens` table, or spam `/me/link` with invalid tokens.

**Recommendation:**
Standard API rate limiting for authenticated endpoints should be sufficient, but placing stricter rate limiters specifically on auth/linking endpoints is a best practice.
